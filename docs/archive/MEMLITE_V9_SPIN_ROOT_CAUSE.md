# MEM-Lite v9：模拟器原地打转的根因诊断与修复方案

诊断日期：2026-09-07。对象为 `behavior5_memlite_ar_v9_train_20260906T031051Z/checkpoints/step_5000.pt`，纯 AR 推理。本次没有修改主仓库、模型权重或训练数据，没有重训，也没有重新计算正式成功率。

**09月08日补充：** 后续v10改进训练已完成，转换窗口审计发现了额外的动作编码失真。原2.2节的结论不能推广为“所有停转窗口的codec都没问题”；新增证据见第7节。原v9因果探针与后续v10结果分开保留。

## 结论

核心问题在策略决策及其闭环恢复：模型会选择持续转向的动作序列，底盘速度反馈又会明显影响、甚至压过“该停止转向/改变运动方式”的决策；高层长期保持同一意图，未能打断循环。

这不是已经定位到某一行“正负号写反”的代码错误。已经有直接实验支持速度反馈是重要因果因素，但尚不能声称它是唯一原因，更不能声称把输入速度清零就能解决整个任务。

最合理的修复方向是：**训练低层的目标驱动转向终止/换向能力，降低对当前速度的捷径依赖，并用真实失败—恢复数据让高层具备纠偏能力。** 仅增加训练步数、减小转速上限、扩大 memory 文本，均不构成已验证的根治。

## 1. 原评测究竟发生了什么

对五个任务的策略侧和模拟器侧全部 70,126 个 23 维动作逐项比较，完全一致。不存在“模型输出正确，但桥接时传成另一个动作”的现象。

| 任务 | 总动作步数 | 平均 yaw 指令 | yaw > 0.05 的步数比例 |
|---|---:|---:|---:|
| turning_on_radio | 3,225 | +0.28743 | 99.94% |
| picking_up_trash | 7,902 | +0.18276 | 79.06% |
| putting_away_Halloween_decorations | 20,683 | +0.17671 | 78.40% |
| cleaning_up_plates_and_food | 20,545 | +0.16211 | 73.83% |
| can_meat | 17,771 | +0.04760 | 32.36% |

yaw 是底盘角速度控制指令，该轴控制器输入/输出缩放比为 1；训练动作支持约为 ±0.30。平移轴另有 0.75 的控制器缩放，不与 yaw 混用。

radio 不是小幅量化漂移：其 3,225 步全部为正 yaw，其中 3,223 步 > 0.05，后期长期接近 +0.29。201 个完整的 16 步执行块中，只有 42 个不同的底盘动作块，最常见块精确重复 57 次。

我人工查看了原评测头部相机在请求 1、129、257、641、769 的截图：初始画面朝向电视/壁炉；129、257 时红色收音机已经可见，257 时清楚地在前方桌上，但后续 16 步平均 yaw 仍为 +0.27362，之后继续转动，又回到了电视方向。因此，最初转向寻找目标可能合理，**找到目标后仍不能结束转向**才是关键失败。

## 2. 已排查的执行和表示层问题

### 2.1 底盘速度没有被当成相对位姿累加

实际流程为：AR tokens → ActionCodec 解码 → 反归一化 → 拆分 `lower_body = trunk(4) + base_qvel(3)` → 输出官方 23 维动作。

`BehaviorPerKeyTransform.backward` 只对配置中的躯干相对位置维度和双臂加回当前状态；底盘三维速度直接拆出，没有加上当前底盘速度。

证据：[本次主仓库快照 relative_action.py](memlite-spin-diagnosis.SqVGCy/source_snapshot/src/g05/data_processor/transforms/relative_action.py)，重点为 711–740 行。不能再套用早期底盘 mask 漏训问题解释这一轮：本轮明确生成、解码并执行了底盘动作。

### 2.2 常值停转可准确表示，但这不覆盖所有转换窗口

使用本次训练运行实际保存的 `action_tokenizer.pt` 和 train-only 统计量，在 CPU 上完成 42 个独立表示测试：25 个真实 heldout 动作窗口，17 个合成常值底盘指令窗口。

| 输入 yaw | 解码后前 16 步 yaw 平均绝对误差 |
|---:|---:|
| 0 | 0.000420 |
| +0.05 | 0.001481 |
| −0.05 | 0.000991 |
| +0.15 | 0.001666 |
| −0.15 | 0.001081 |
| +0.28 | 0.000964 |
| −0.28 | 0.001155 |

上述合成常值停转输入的最大 yaw 误差仅 0.000808，远小于原评测持续的 +0.287。编码器具备表示常值停止和双向转动的能力；这排除了“任何零动作都会被解成持续大幅正转”的解释，但不排除尚未覆盖的转换窗口失真。不能靠修改符号或均值还原解决策略选择问题。

### 2.3 不是 A100 推理慢造成动作意义变化

慢影响评测墙钟耗时。当前记录显示模拟器实际收到了持续同向旋转指令，而且记录动作回放也产生了真实转动；没有证据表明缩短推理等待即可纠正这些动作决策。

另外检查了官方 LeRobot 数据写入器：它将前一条观测和随后执行的动作配对，不是直接把执行后观测当成执行前输入。训练数据示例中，转速状态也滞后于控制指令变化。这里发现的强相关不能被直接叫作“未来动作泄漏”。

## 3. 对同一份权重做的因果探针

### 3.1 原始输入可复现

直接读取原评测保存的五个 `first_official_observation.msgpack`，固定原始意图，重新运行同一权重。五个任务的首个 16 步底盘动作都与原日志逐项一致。这验证了本次模型探针确实在检查原运行的策略行为。

### 3.2 速度输入确实能改变转向决策，但不是唯一输入

固定 radio 原始初始画面、任务、意图和其他关节状态，只替换初始历史中的底盘转速：

| 输入 yaw | 预测的前 16 步平均 yaw |
|---:|---:|
| 0 | +0.21055 |
| +0.15 | +0.25270 |
| −0.15 | +0.21055 |
| +0.30 | +0.26597 |
| −0.30 | −0.25405 |

这排除了“永远只能输出正转”的硬编码解释，也说明不是简单线性复制当前速度：零速度仍可触发主动转向，视觉变化也能改变输出。

### 3.3 转起来之后，速度反馈会锁住动作模式

在模拟器中执行原 radio 的前 1,024 条记录动作，不调用策略决定执行动作；保存每 16 步的真实 RGB 和 proprio，再重建 6 帧、间隔 16 步的输入历史。随后分别查询同一权重的正常输入和只改变底盘速度历史的输入。

| 回放观测位置 | 正常输入：平均 yaw | 速度历史置零：平均 yaw | 速度历史置零：平均 x 指令 |
|---|---:|---:|---:|
| 执行完 128 步 | +0.29194 | −0.00050 | +0.27754 |
| 执行完 256 步 | +0.27362 | +0.00124 | +0.28497 |
| 执行完 512 步 | +0.27927 | +0.14486 | +0.00070 |
| 执行完 1,024 步 | +0.28053 | +0.00186 | +0.31700 |

256 步处，反转输入 yaw 历史又会让预测 yaw 变为 −0.28771。画面、任务、意图、其他关节输入完全不变，只有速度历史改变。这是速度输入对运动模式存在因果影响的直接证据。

但置零并非万能：16、64、384、512、768 等位置仍预测一定旋转；置零后预测“前进”也没有被专家验证为正确动作。因此这些结果**不支持直接把线上速度输入全部清零并宣布修复**。

回放的保真边界：回放初始 proprio 与原记录完全相同，但初始 RGB/视角不同，我已人工查看并确认，不能称为原评测逐帧重现。256、512 步处未干预查询的底盘动作与原日志完全一致，其他位置存在差异。上表是成对控制输入实验，不是新的闭环成功率，也不证明干预后的下一段轨迹会成功。

回放另外测得 1,024 步内实际转过 8.578 rad（1.365 圈），净平移仅 8.65 mm；这些位姿只用于诊断，没有输入给模型。

## 4. 为什么训练允许这种行为

以下是已统计的训练诱因和设计缺口，不等同于完成了重训消融。

### 4.1 延续当前速度是一条非常便宜的训练捷径

读取全部 950 个训练 episode、8,898,502 帧原始动作和状态，没有使用 eval episode：

| 任务 | 当前 yaw 与专家动作 yaw 的相关系数 | 当前已正转时，专家立即停转的帧比例 |
|---|---:|---:|
| radio | 0.9887 | 3.03% |
| trash | 0.9902 | 1.51% |
| Halloween | 0.9914 | 1.02% |
| plates | 0.9814 | 2.02% |
| can | 0.9761 | 1.44% |

定义：已正转为 state yaw > 0.05；停转为 action |yaw| ≤ 0.01。统计是所有原始训练帧，不是仅低层可采样帧，也不是训练期间实际交付 batch 的逐项收据。

radio 全体帧中 82.13% 是停转，但“已经转起来、这时应当刹住”的状态少得多。它的训练 yaw 均值甚至是 −0.00302，并不普遍偏向正转。**因此问题不是数据里所有人都在向右转，而是条件分布中“继续转”远比“现在结束转向”容易学。**

这符合行为克隆中的因果混淆机制：模型能利用训练相关性，却不一定学会在自身动作改变未来输入后做正确决策。它是对本轮实验的解释，不是用论文代替本机证据。[Causal Confusion in Imitation Learning](https://arxiv.org/abs/1905.11979)

### 4.2 整体 CE 不能证明动作决策可靠

本次在先前验证过标签/动作/窗口一致性的 25 个 heldout 窗口上，给定真实 intent，同时保存 teacher-forced token 概率和自由 AR 输出。

格式 token 的 teacher-forced top-1 为 100%，但躯干/底盘两层动作码的 top-1 分别只有 66.5% 和 60.0%；双臂动作码为 16%–22%。这些是活动选择的小样本诊断，不是全 eval 集指标，也不能把 token 精确匹配率直接换算成物理动作正确率。

在 Halloween episode 590 frame 1，专家前 16 步平均 yaw 约为 0，而自由生成均值为 +0.21055；对应真实动作通过编码器重建时 yaw MAE 仅 0.00246。错误已经存在于给定真实 intent 的动作选择中，而不是完全由高层错误诱发。

因此训练应当单独考核启动、转向结束、换向和恢复状态，不能只凭一个混合平均 CE 认定策略“已经会做”。更长训练可能有帮助，但本轮没有证据证明仅增加步数就会解决它。

### 4.3 高层目前不能有效打断循环

原评测中，高层分别执行了 26、62、162、161、139 次，五个任务各自从头到尾都只输出同一个意图。radio 始终是：

`pick up from [radio_89 coffee_table_koagbh_0 -> radio_89]`

服务端已经按约 128 个执行动作重算高层，所以不是简单“没有重新调用 planner”。问题是重新调用后决策不变。

目标未完成时维持同一意图本身可以合理；不能仅凭意图重复判定 planner 错误。这里真正的缺口是持续无进展时也没有产生有效的恢复行为或状态切换。

当前低层 builder 只消费 task、intent、proprio 和图像；它没有一个单独受监督的转向终止/进度判断。高层 causal 标签主要来自成功示范中的 CONTINUE/DONE，以及文本 memory 缺失/过早宣称完成的扰动。代码明确没有由此生成真实失败观测和成功恢复轨迹。协议支持 FAILED/REPLAN，不代表模型学会了何时正确输出它们。

证据：`IntentActionBuilder.template`、`build_memlite_annotations.py` 的 causal high-label 构造和文本 corruption 段，以及 `serve_policy_mem.py::_causal_actions`。

## 5. 建议的一个完整修复方案

保持高低层 MEM-Lite 和纯 AR 主架构，不急于换回 FM，也不先重做 ActionCodec。按以下顺序修复同一个闭环问题。

### A. 低层训练：让“何时改变运动”成为主要监督

1. 在原训练实例中，从原始专家动作生成底盘状态/转换标签：静止、正转、反转、平移、转动结束、启动、换向。标签用于采样和损失统计；必须查看整个执行窗口，不能仅用平均 yaw（正负抵消会伪装成停止）。
2. 逐 task、逐状态转换分层采样，提高转动结束/启动/换向窗口占比，并保留正常巡航和静止样本。不能只增加普通静止帧——模型在“已经转动”的条件下仍会缺少刹车训练。
3. 对进入模型的底盘三维速度历史施加带显式缺失标记的 dropout，破坏“直接延续速度”的捷径；只干预模型条件，保留真实状态用于动作还原和监控。训练、推理必须使用一致的缺失表示，不能把“未知速度”冒充“机器人已停住”。可先用 50% 作为待验证起点，并以固定全遮蔽作小规模机制对照；不是已经验证的最优超参。
4. 保留现有 codec，但单独统计/适当加权 lower-body 动作码和关键转换窗口的 CE。若需要新增轻量 `base_mode` 分类辅助头，用专家动作构造监督，迫使视觉+意图表示区分该转、该走、该停；第一版不让未经验证的辅助头硬覆盖实际动作。

### B. 数据：补上真实的“犯错后怎么办”

在**训练场景/训练实例**中复现转过头、目标偏离视野、方向错误等状态，收集人工或可靠专家的纠正动作，形成“停止转动—重新对准—接近目标”的完整观测/动作轨迹，混入原成功示范训练。

不能只改成功轨迹的 memory 文本，就把它称为恢复训练；也不能任意改 yaw 数值后保留原动作作正确标签。模型自身到达的失败状态需要正确的行动监督。这是 DAgger 类数据聚合所针对的分布偏移问题。[DAgger 原论文](https://proceedings.mlr.press/v15/ross11a.html)

**本轮 public-test 301 的失败轨迹只用于诊断，不并入训练。** 修复后仍保留独立评测，避免把验证问题变成测试集记忆。

### C. MEM 高层：建立“观察进展—触发恢复”的闭环

为真实恢复轨迹补上因果一致的 `progress/no_progress`、`intent_status=REPLAN` 和恢复 intent；memory 记录已观察到的停滞和失败，不编造已经完成的动作。

增加执行侧的无进展检测：结合允许的 RGB、真实 base_qvel 和动作历史，识别长时间同向转动、视野重复而任务没有可观测进展。触发暂停/请求恢复方案，而不是把同一 intent 无限重复。阈值需要在训练实例上校准，不能把正常寻找目标的转向全部禁止；不能使用评测接口未提供的机器人全局位姿或真实目标坐标作为模型输入。

这层监控是防止无限循环的护栏，不是成功策略本身。固定 yaw=0、强制一直向前、只缩短 action chunk 均不能替代 A/B。

### D. 验收：不以“暂时不转了”为成功

先用训练/验证分离的真实窗口检查：转动结束召回、必要转向召回、换向正确率、物理 yaw 误差、自由 AR 解码。必须同时评估“该停能停”和“该转能转”，防止永远输出零动作获得漂亮指标。

再在固定、保存完整初始模拟器状态的实例上闭环验收：目标进入视野后能否完成对准和接近；出现偏差能否恢复；是否仍存在长时间重复转圈；最终以官方任务进度/成功率判断。沿用已有 v9 结果作历史参照，不需要重跑已取消的基线评测。

在这些检查通过之前，不建议直接再投入一轮完全相同的 5,000 步训练。

## 7. 09月08日新增：32步动作压缩会污染前16步的刹车目标

在v10训练完成后的307样本检查中，12个真实留出恢复刹车窗口的前16步专家底盘指令全为零，后16步通常开始重新对准。模型只有1/12满足“前16步末四步均 |yaw|≤0.02”的停转条件。为判断是否只是预测错误，我对全部271个低层样本独立做了CPU codec往返审计，不调用VLM、不更改数据或权重。

| 检查 | 恢复刹车12例 | 普通停转40例 |
|---|---:|---:|
| 模型实际预测通过停转条件 | 1/12 | 15/40 |
| 专家真实动作编码为正确token，再直接解码 | 1/12 | 37/40 |
| 仅将后16步底盘指令保持为第16步的值，再编码解码 | 12/12 | 40/40 |

第三行是明确的**编码输入反事实**：前16步所有真实专家动作完全不变，仅改动还不会执行的后16步底盘指令。这直接证明，当前32步整块编码/重建会让后段动作影响前段停转的表示。它不是传感器未来信息泄漏，也不是证明整个码本无能力表示停止。

三个恢复例子的底盘token教师强制准确率已为100%，自由预测的前16步底盘动作与正确token重建的最大差异仅约6.2e−6，但末四步yaw约0.046–0.050，仍不满足刹车条件。另外一些例子同时存在模型选错token的额外误差；不能将所有失败都归给codec。普通停转中37/40的目标编码可以停，模型却只停15/40，也明确说明低层转换决策仍不足。

因此后续应首先验证**动作token监督与实际16步执行区间的一致性**：例如以真实前16步为监督单位，后半段只作保持填充，或者使用分块独立/因果的动作编码；对底盘停转、换向和夹爪事件验证编码往返误差后，再决定新一轮训练。保持填充目前只完成了上述底盘反事实诊断，尚不是已验证的全动作训练方案，也没有把它偷偷应用到已训练的v10模型。

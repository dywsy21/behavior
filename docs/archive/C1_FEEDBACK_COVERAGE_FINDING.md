# 反馈采集的结构性覆盖缺口

2026-09-11；本人代码复核。此发现解释为什么“再多采几批相同GRASP窗口”不能自动补齐四类反馈，不是把超时伪标为FAILED的理由。

## 已证实的代码事实

1. 现有C1窗口选择器只接受单一GRASP，并以演示前缀抵达该技能开始位置：`prepare_c1_windows_v2.py`中的`len(semantic)==1`和`verb==GRASP`筛选。
2. `c1_v2/c1_feedback/feedback_c1.py:720`将未提供的`failure_reason_provider`设为`lambda: {}`。当前官方C1工厂和新C2工厂构造driver时均未接入实际物理失败原因提供器。
3. 当前GRASP物理oracle对明确未持有返回IN_PROGRESS；只有有效显式物理失败证据才会进入FAILED，而超时/块结束被明确排除。该保护应当保留。
4. `feedback_c1.py:852`在首次达到新的稳定SUCCEEDED之后就停止当前局部采集。因此，成功之后的握持丢失、运输中的滑落及实际恢复不会被该窗口采集器观察。

## 直接后果

当前这类固定GRASP窗口主要只能收集进行中和首次成功，另有不可判断的UNKNOWN。FAILED不足不是单纯的随机样本量问题：失败提供器未接入、技能范围受限、成功后立刻停止，共同使许多真正需要的失败/恢复事件在采集设计上不可见。

所以仍不能训练并声称验收了一个完整的成功/失败/进行中/UNKNOWN结果头；也不能将1280步预算用完的样本改为物理FAILED补齐类别。原数据和原oracle均不修改。

## 接下来应实施的独立采集版本（本文件不是实施完成声明）

- 扩展到有明确物理后置条件的抓取后维持/搬运、开门和放置，保留当前意图、实际执行控制和每个真实物理帧的可观测历史。
- 允许有界地继续观察首次成功后的过程，单独记录事件，而不是给已经完成的局部技能虚构未来反馈。
- 对每类FAILED先写出可复核物理定义及反例。例如“意外丢失已确认抓持”必须有之前连续稳定持有、之后连续失去、同一目标和实际意图/控制上下文；主动RELEASE/PLACE、读数不明或仅暂未抓到不得判为该失败。
- 失败提供器只在评测/采集侧读取物理状态，绝不把特权真值投影进部署模型输入。缺失条件继续UNKNOWN或IN_PROGRESS。
- 真实纠正仍必须来自另一控制器/人工从原失败状态接管，实际成功后才进入独立复放和本人逐段语义审核；演示回放只能是单独标识的回放诊断，不冒充学习器失败后的纠正。
- 上述新采集与模型训练要保持训练实例/原5%eval/反复使用public_test实例隔离；完成真实类别覆盖、实例级切分、人工审核后再决定反馈头及交替协同训练。

这是下一轮数据采集逻辑需要修正的具体瓶颈，而不是一个靠多训步数或继续等待即可满足的验收门。
